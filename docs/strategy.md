# Dayopt コンセプト

## 1. なぜ作るか（原体験）

- Google カレンダーを何年も使ったが、**記録するだけで意味が生まれなかった**。「それだけになっててよく分からない」状態。入力も面倒だった
- 最初は ClickUp のようなタスク管理（ボード・テーブルビュー）を作ったが、**違った**。必要なのは 3 ステップくらいで簡単に予定が立てられて、かつ**抽象的でいい**こと
- 例: 「開発」カテゴリーの下に「API」アクティビティがある。それを押して「2時間やった」で基本的に終わり。詳細（仕様書・成果物・タスクの中身）は GitHub Issues や Notion にあり、Dayopt が持つ必要はない。必要ならリンクを貼ればいい
- だからタスク管理ツールとの併用が前提。創業者自身、GitHub Issues をやめる予定はない

## 2. ジョブと売り物

```
ジョブ        : 計画を守れるようにする（「計画を守れない」を解決する）
手段          : 予定と実績を 1 つのタイムラインに重ね、ズレを理解できるようにする
得られる価値  : 進捗感（進んでいる感覚）と「自分を高めている」感覚 — これが続ける理由になる
```

**「ズレを見せる」は手段であって売り物ではない。** 誰も朝起きて「自分のズレが見たい」とは思わない。欲しいのは「立てた計画がその通りに進む日」。ズレはそこへ至るための計器。

> **一文コンセプト: Dayopt は、予定と実績のズレを毎日の学習に変え、「守れる計画」を立てられるようにする、いちばん軽いタイムボクシングツール。**

英語の約束: **"Plan days you can actually keep."**

使い続けると起きること: 作成時に統計が「30分の予定だが、この作業の実績は45分」と教えてくれる → 見積もりを直す → 計画が守れるようになる → 見積もり精度が上がっていく。

## 3. ターゲット

**AI を使いこなす知的労働者。** タスク管理や情報整理はすでに AI や既存ツール（GitHub Issues / Notion / Slack）に任せていて、自分の時間の全体感を見る場所がない人。開発者はその中核だが、開発者に限らない。創業者自身がアーキタイプユーザー。

- 市場は世界中の個人。B2B ではない
- この人たちは Claude / ChatGPT のチャット画面で、複数の MCP（Notion、Slack、そして Dayopt）を横断して「他にやった方がいい活動ある？」「うまい使い方ある？」と聞く。**横断的な考察はチャットでやるのが自然**であり、Dayopt の中に AI チャットは要らない
- Dayopt の役割は、その会話を可能にする**構造化された時間データの正典（source of truth）**であること

## 4. プロダクト原則

1. **参照するが、所有しない。** Dayopt が所有するのは時間とアクティビティだけ。タスクの詳細・成果物・メモの本体は他ツールの領土で、リンクで参照する。詳細を持たないから 3 ステップで予定が立つ
2. **ブロックは抽象でいい。アクティビティが語彙。** 入力の最小単位はタスクではなくアクティビティ（所属は最大 1 カテゴリー: `開発` の下に `API` 等）。タイトル欄は存在しない。あるのはアクティビティ + 一言メモ欄（リンク貼付可）だけ。カテゴリーの入れ子や自由なメタデータは分類管理という新しい摩擦を生むので許さない
3. **自動生成はゴーストまで。確定は人間のワンタップ。** ルーティン（繰り返し）、AI の書き込み（MCP/API 経由）、外部カレンダーの予定 — どこから来ても未確定のゴーストとして現れ、クリックで実際のブロックになる。無視すれば消える。この単一概念で「自動化の便利さ」と「選択型ログの主体性」を両立する
4. **記録の確定は人間の儀式。** 自己記録の効果（達成感・行動変容）は人間の手で確定するから生まれる。API は書き込みも開けるが、UI 設計は常に「人間の 1 タップ確定」を最短経路に置く
5. **データの正直さを壊さない。** 時間の規則は 2 本だけ —— 「終了は開始より後」と「記録（実績）を未来に置けない」。（invariants.md / specs/plan-record.md と同じ数え方にする。この文書は衝突時に優先すると自称しているので、数が食い違うと誤った方が勝ってしまう）予定は過去・未来を問わず自由に編集でき、あとから実際の時間へ訂正できる。かつては「ズレの捏造を防ぐ」ために過去の予定を凍結していたが、削除は無条件にできるのに時刻の訂正だけができない非対称が実運用の摩擦になったので撤回した（2026-09-04）。正直さは予定を凍結することではなく、記録がユーザーの明示的な確定でしか生まれないこと（原則 4）で担保する
6. **進捗は報酬ではなく証拠で見せる。** バッジ・点数・ストリーク演出はしない。「このアクティビティの見積もり精度、4週間前より上がっています」「先週守れなかった計画が今週は守れました」という過去の自分との事実比較だけが進捗感の源泉。比較対象は常に過去の自分
7. **通知はユーザーの計画に仕える。アプリの都合で鳴らさない。** ブロック開始・終了の合図（opt-in）は「自分が頼んだ合図」であり OK。streak 煽り・離脱メール・re-engagement push は永久に禁止
8. **AI は外にいる。** in-app の AI 機能は作らない（少なくとも初期は）。MCP / API であらゆるデータを読み書きできるようにし、ユーザーが自分の AI（Claude / ChatGPT）を接続する。統計的なフィードバック（見積もり実績の提示、週次の補正提案）はルールベースの計算で十分成立し、AI を必要としない
9. **軽い・早い・少ない。** 速度・起動の速さ・操作数・画面の少なさは機能要件。Sunsama を重さで、Motion を「勝手に動かされる不信」で相対化するための武器
10. **ズレは部屋ではなく、瞬間に置く。** 今日のズレはカレンダーの上と脇のパネルに分散して現れ、そこから消さない。`/report` は「問いを持って見に行く場所」として存在してよいが、**レポートビルダーにはしない** — 期間指定の複雑なフィルタ・カスタムレポート・保存フィルタの入れ子・グルーピングの自由化は足さない（Toggl / RescueTime の領土）。分析を「行き先」にすると分析が目的化する、という歯止めの理由は変わらない。具体的な分散先の設計は [`principles.md`](./product/principles.md)

## 5. 変えないもの

1. **予定と実績が同じタイムラインで対になる設計**（ADR-011（削除済み、git 履歴参照） → ADR-025（削除済み、git 履歴参照）） — 計画と実績を1画面で突き合わせられることが本物の差別化。実装モデルは 1 Entry から Plan / Record 分割（1予定:N記録）へ発展したが、この本質は変わらない
2. **Todo エンジンを作らない** — サブタスク・優先度・期限・ボード・テーブルは作らない（一度作って捨てた）
3. **他人と比較しない・gamification をしない**
4. **$5 価格帯** — 「AI と連携できて、全体感が見えて、カレンダーと紐づく」なら $5 は払う。$10-20 だと微妙。この感覚を維持する
5. **軽さ・速さ・少なさ**

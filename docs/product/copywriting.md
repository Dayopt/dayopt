# Dayopt Copywriting Tone Guide v3

## 人格定義

> **「あなたの時間に関心を持っている、寡黙な研究者」**

データで示し、感情で煽らない。ユーザーの知性を信頼し、結論を押しつけない。必要な事実を静かに伝え、毎回コメントを足さない。具体的な機能や節目の扱いは、製品仕様を正本とする。

この人格が最優先の判断基準である。本書後半の説得の技法（チャルディーニ6原則・表現の順序とメタファー）は、人格に従属する道具にすぎない。技法と人格が衝突したら、常に人格を優先する。Do / Don'tチェックリストの禁止事項（他人比較、恐怖を煽る訴求、煽情的な表現）は、この序列を具体化したものである。

この人格はプロダクト（UI）の声である。ブログやSNSなどのマーケティングコンテンツは、創業者の人間臭い声で書く。正本は[`docs/business/content/voice.md`](../business/content/voice.md)である。二つの声は意図的な使い分けである。

### 性格ルール

| 場面 | 研究者はこう語る     | こうは語らない       |
| ---- | -------------------- | -------------------- |
| 変化 | 先週より30分多いです | すごいですね！       |
| 差異 | 先週より短めでした   | もっと頑張りましょう |
| 沈黙 | 必要な情報だけを表示 | 毎回コメントを添える |

### 距離感の基準

- 日常操作（トースト、エラー）：最短の言葉。感情を載せない
- 週次・月次・年次のレポート：表示内容や文言は[振り返り仕様](./specs/review.md)に従う
- 節目：機能や演出の有無は製品仕様に従い、コピーだけから追加しない

| 7   | エラーに原因+対処を含める     | エラーが発生しました               | 問題が起きました。もう一度お試しください |

## 英語UI文言ルール

人格は言語をまたいで同一である。日本語の「です・ます」に相当する丁寧さは、英語では平易で直接的な文で表す。翻訳ではなく、各言語で自然な文を書く（正本は `apps/product/messages/{en,ja}/`、運用は i18n skill）。

| #   | ルール                          | NG                           | OK                               |
| --- | ------------------------------- | ---------------------------- | -------------------------------- |
| 1   | sentence case（文頭のみ大文字） | Delete Event                 | Delete event                     |
| 2   | ボタンは動詞で始める            | Deletion                     | Delete                           |
| 3   | 短く直接的に。please で飾らない | Please try again later       | Try again                        |
| 4   | 主語 your は必要な場合のみ      | Your profile                 | Profile                          |
| 5   | destructiveボタンに対象を明記   | Delete                       | Delete event                     |
| 6   | エラーに原因+対処を含める       | An error occurred            | Something went wrong. Try again. |
| 7   | vague SaaS words 禁止           | Seamlessly optimize your day | See where your time went         |

- 性格ルールと感嘆符の基準は日本語と共通。事実の比較は「30 min more than last week」のように簡潔に書く
- 7 の禁止語リスト（empower / leverage / seamless / robust / optimize など）は [writing-style.md](../business/content/writing-style.md) §英語のルール と共通

## 感嘆符の使用基準

| 場面               | 使用 | 例                                   |
| ------------------ | ---- | ------------------------------------ |
| 日常操作           | ×    | 保存しました（✓で代替）              |
| 日常の操作トースト | ×    | 削除しました（✓で代替）              |
| エラー             | ×    | 問題が起きました。                   |
| 空状態             | ×    | 最初のブロックを記録して始めましょう |

感嘆符は日常では使わず、製品仕様が許す場合に限って使う。✓マークや事実の提示で結果を伝える。

## チャルディーニ6原則の適用

Dayoptは、押しつけずデータで示す影響力の研究者としてチャルディーニのように語る。以下の原則は、人格定義の序列に従う道具である。

### 原則1: 一貫性（Commitment & Consistency）

ユーザーが「自分はこういう人間だ」と感じる言葉を使う。小さなコミットメントを積み上げさせる。

| 場面                     | NG                             | OK                                             |
| ------------------------ | ------------------------------ | ---------------------------------------------- |
| 空状態（初回）           | まだデータがありません         | 最初のブロックを記録して始めましょう           |
| 空状態（アクティビティ） | まだアクティビティがありません | 最初のアクティビティを作って整理を始めましょう |
| オンボーディング         | プロフィールを入力してください | 朝型？夜型？あなたのリズムを教えてください     |
| 空状態                   | まだ予定がありません           | 最初の予定を追加しましょう                     |
| 結果                     | すごいですね！                 | 先週より30分多いです                           |

**ルール: 空状態では「ない」で終わらず、次の一歩を具体的に示す。製品機能・指標・画面の有無や意味はここで定義しない。**

### 原則2: 希少性（Scarcity）

得るものではなく、失うものをフレーミングする。ただしボタンではなく説明文で表現する。

| 場面     | 説明文（希少性）                         | ボタン（ニュートラル） |
| -------- | ---------------------------------------- | ---------------------- |
| 削除確認 | この記録は完全に消えます。取り消せません | 記録を削除             |

**ルール: 心理的圧力は説明文が担う。ボタンは押しやすさに専念する。**

### 原則3: 好意（Liking）

味方の研究者として寄り添う。責めない、データで褒める、安心感を与える。

| 場面         | NG                     | OK                                               |
| ------------ | ---------------------- | ------------------------------------------------ |
| 成功トースト | 作成しました           | 記録しました ✓                                   |
| パレット追加 | パレットに追加しました | パレットに追加しました。次回からすぐ使えます     |
| 記録ゼロの日 | 記録がありません       | 今日の記録を始めましょう                         |
| 中度エラー   | 保存できませんでした   | 保存できませんでした。入力内容は保持されています |

**ルール: 成功には小さな達成感を添える。失敗・空白は責めず、必要なら次の行動を示す。変化は事実として伝え、感情的に煽らない。**

### 原則4: 社会的証明（Social Proof）

他人のデータは使わず、「過去の自分」を証人にする。

| 場面       | NG                 | OK                                   |
| ---------- | ------------------ | ------------------------------------ |
| 結果       | すごいですね！     | 先週より30分多いです                 |
| 未確認情報 | きっと集中できます | 表示するデータがない場合は断定しない |

**ルール: 実際に確認できる事実だけを書く。比較対象・レポート指標・集計の定義は [振り返り仕様](./specs/review.md) を参照する。**

### 原則5: 権威（Authority）

Dayoptが時間管理の「正しいやり方」を再定義する存在として語る。

| 場面             | NG                   | OK                                                               |
| ---------------- | -------------------- | ---------------------------------------------------------------- |
| LPキャッチコピー | 時間を管理しましょう | カレンダーは予定を見せます。Dayoptは実際に何が起きたかを見せます |
| 機能説明         | 便利な機能です       | 予定と記録を並べて表示します                                     |

**ルール: 機能説明ではなく、なぜそれが正しいのかの根拠を暗示する。**

### 原則6: 返報性（Reciprocity）

まず価値を与えてから求める。

| 場面     | NG             | OK                             |
| -------- | -------------- | ------------------------------ |
| 価値説明 | 便利な機能です | 予定と記録を並べて確認できます |

**ルール: 課金を求める前に、具体的な価値を先に提示する。**

## 表現の順序とメタファー

価値や可能性をコストより先に述べるときも、実在しない便益・機能・価格条件を追加しない。質問の前置きでは、これまでの「Dayoptで良くなった点はありますか？」のように求める観点を具体的に示す表現を使う。

一般的な説明のメタファーは「地図」で統一する。ただし「見積もりの鏡」など製品仕様にある固有の名称を禁止するものではない。例:「時間の地図を作る」。実際の画面用コピーは各機能の仕様に従う。

## 製品契約との境界

この文書は口調・文章表現の指針であり、機能、価格、通知、レポート指標、AI、画面遷移の採否を決めない。例文は機能の存在や提供時期を約束しない。実際の製品契約は次を正本とする。

- 製品原則と不採用方針: [strategy.md](../strategy.md)、[product principles](./principles.md)
- 価格・提供範囲: [価格戦略](../business/pricing.md)、[Billing spec](./specs/billing.md)
- レポートの現在の指標・表示・文章方針: [振り返り仕様](./specs/review.md)
- 現在の画面・操作仕様: 該当する `product/specs/*.md`

正本にない機能や未決の目標を、例文だけを根拠に実装済み・採用済みとして扱わない。製品判断が変わった場合は、まず該当する正本を更新する。

## 数字と比較の書き方

数字は根拠と対象期間を確認できる場合だけ使う。指標、比較方法、期間、閾値は文章ガイドで定義せず、[振り返り仕様](./specs/review.md)に従う。比較データがない場合は比較を作らず、表示された値を中立に伝える。順位、スコア、ストリーク、平均や推奨を、例文から製品要件として導入しない。

## CTAの強度階層

### Tier 1: 重要なCTA

契約・購入の文言や提示条件は [価格戦略](../business/pricing.md) と [Billing spec](./specs/billing.md) に従う。このガイドだけから Free 制限、Pro、課金導線や希少性の訴求を作らない。
視覚: Primary（塗りボタン、アクセントカラー背景）。1画面に最大1つ。

### Tier 2: 行動CTA（機能利用・記録開始）

一貫性を使う。具体的な行動を示す。

| 場面         | NG       | OK                       |
| ------------ | -------- | ------------------------ |
| 空状態       | 追加     | 最初のブロックを記録する |
| テンプレート | 使用する | このテンプレートで始める |
| パレット     | 登録     | パレットに追加する       |

視覚: Secondary（アウトラインボタン）。

### Tier 3: 情報CTA（詳細確認・ナビゲーション）

ニュートラル。心理的圧力ゼロ。

| 場面         | NG                   | OK         |
| ------------ | -------------------- | ---------- |
| 設定への導線 | 設定を開いて確認する | 設定を見る |
| 詳細         | 内容を確認する       | 詳しく見る |
| ヘルプ       | ヘルプページへ移動   | 詳細       |

視覚: Ghost（テキストリンク、下線 or アイコンのみ）。

### CTAルール

| #   | ルール                                                        |
| --- | ------------------------------------------------------------- |
| 1   | Tier 1は説明文が心理的な仕事をし、ボタンはニュートラル        |
| 2   | Tier 2は具体的な行動動詞で書く                                |
| 3   | Tier 3は最小限の言葉                                          |
| 4   | 1画面にTier 1は最大1つ                                        |
| 5   | 抽象的な動詞を避ける（「使用」「確認」→「記録する」「見る」） |

## 通知・復帰導線

通知の採否、種類、配信条件は [strategy.md](../strategy.md) と [product principles](./principles.md) を正本とする。このガイドは通知や復帰バナー、メールの存在を定めず、復帰を促す導線やコピーを追加する根拠にもならない。採用済みの通知・メールがある場合は、その機能仕様に従って表現を決める。

## エラーの重要度階層

| 重要度               | 表示方法           | 例                                                                           |
| -------------------- | ------------------ | ---------------------------------------------------------------------------- |
| 軽微（コピー失敗等） | トースト           | コピーできませんでした。もう一度お試しください                               |
| 中度（保存失敗等）   | トースト + 安心感  | 保存できませんでした。入力内容は保持されています。もう一度お試しください     |
| 重大（データ競合等） | インラインアラート | このタイムブロックは他の場所で変更されました。最新データを読み込んでください |

中度エラーでは「入力内容は保持されています」の一言を必ず添える。ユーザーの恐怖を激減させる。

---

## 確認ダイアログの使い分け

| 操作                       | 確認方法       | 理由                                   |
| -------------------------- | -------------- | -------------------------------------- |
| 不可逆な削除               | 確認ダイアログ | 取り消せないため事前確認が必要         |
| 可逆な操作（アーカイブ等） | Undoトースト   | 「アーカイブしました。元に戻す」で十分 |
| 設定変更                   | 確認なし       | いつでも戻せる                         |

GAFAは確認ダイアログを減らす方向。不可逆な削除だけ確認を出し、それ以外はUndoトーストで対応する。

## カテゴリ別テンプレート

### トースト通知

```
成功:      「{操作}しました」 or 「{操作}しました ✓」
失敗（軽微）: 「{操作}できませんでした。もう一度お試しください」
失敗（中度）: 「{操作}できませんでした。入力内容は保持されています。もう一度お試しください」
Undo:      「{操作}しました。元に戻す」
```

### 空状態

```
初回:    可能性を先に置く。「{ポジティブな観察}。最初の{対象}を{動詞}ましょう」
検索:    「「{キーワード}」に一致する{対象}がありません」
期間:    「新しい{期間}が始まりました」
```

### 削除確認

```
基本:    「{対象}は完全に削除されます。取り消せません。」
関連あり: 「{対象}と{n}件の{関連}との紐づけが消えます。取り消せません。」
```

### 課金・契約に関する文言

価格、プラン名、無料体験、利用状態ごとの操作範囲は [価格戦略](../business/pricing.md) と [Billing spec](./specs/billing.md) の現行記述を使う。旧プラン名や機能制限をこのテンプレートから再導入しない。

## Do / Don't チェックリスト

### Do

- 「です・ます」で丁寧に（GAFA準拠）
- 数字は根拠と対象期間を確認してから使う
- 空状態で次の一歩を促す（一貫性）
- 成功に小さな達成感を添える ✓（好意）
- 不可逆な操作では、結果と取り消せないことを明確に伝える
- エラーに原因+対処を含める（好意）
- 中度エラーに「入力内容は保持されています」を添える（好意）
- 製品機能・価格・計測値は各正本に照らして書く
- 可逆な操作はUndoトーストで対応（GAFA準拠）
- 空状態では、必要に応じて次の操作を具体的に示す

### Don't

- 体言止めで文章を終わらせる（冷たい印象、GAFA非準拠）
- 「〜がありません」だけで放置する（行動を示さない）
- 「失敗しました」だけで終わる（リカバリーがない）
- ユーザーを責めるトーン（好意を損なう）
- ボタンに心理的圧力を詰め込む（説明文の仕事）
- 日常のトーストに感嘆符を使う（研究者は普段叫ばない）
- 他人との比較を出す（絶対に使わない）
- 例文だけを根拠に、未実装・未決の機能を実装済みとして扱う
- 本文書だけを根拠に、製品方針・価格・通知・レポート契約を決める

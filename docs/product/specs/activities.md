# Activities（アクティビティ / カテゴリー）

ブロック（Plan / Record）の活動分類。Dayoptにおけるタスク管理の代替（タスクリストは持たない）。旧タグ機構（epic #2162）を置換したモデルで、当初の3構造のうちセグメントは2026-09-15に撤去し、2構造になった。

## 2構造の役割

| 構造               | 役割                                         | 性質                                     |
| ------------------ | -------------------------------------------- | ---------------------------------------- |
| **アクティビティ** | 予定と記録の単位（最も具体）                 | 無限に増えてよい。色・アイコンは持たない |
| **カテゴリー**     | 所属の主軸。1アクティビティは最大1カテゴリー | 単一所属。色（10色固定）とアイコンを持つ |

カテゴリーは「集計の足し算が合う軸」。カテゴリー未所属のアクティビティは「未分類」として扱う。分析で横断的に見たい時は、`/report` のサイドバーでカテゴリー / アクティビティを出し入れする（[review.md](./review.md) §2）。

## アクティビティ

- 名前は1〜50文字。作成・改名は `createActivity` / `updateActivity`（`updateActivity` が改名とカテゴリー付け替えを兼ねる）
- 色・アイコンを自身は持たず、**所属カテゴリーから継承する**。未分類のアクティビティは中立表示になる
- 並びは名前順（`Intl.Collator` / DB collation）。`sort_order` 列は無く、DnDによる並べ替えは廃止した
- 同名: 同一カテゴリー内では一意（DB制約）。未分類のアクティビティ同士はDB上は同名を許容するが、UI（作成・改名・カテゴリー変更モーダル）は同名を弾く。DB側で未分類の同名を許すのは、一意制約を置くとカテゴリー削除時の未分類化（`ON DELETE SET NULL`）が同名衝突で失敗し、そのカテゴリーが削除不能になる事故を避けるため
- マージ・階層・並べ替えUIは無い（旧タグ機構からの意図的な差分。v1スコープ外）

### アクティビティのアーカイブ

- サイドバーの各アクティビティcontext menu「アーカイブ」から実行する。可逆操作なので確認ダイアログは挟まない
- アーカイブすると選択候補（作成/カテゴリー変更ピッカー）から消える。新規付与は不可
- 既にアーカイブ済みへの操作は冪等no-op
- 復元時に同名の現役アクティビティが既に存在する場合は拒否する。自動サフィックスでの解決はしない

### アクティビティへの付与ガード（アーカイブ済み）

- DB command境界（`assert_active_timeblock_activity_v1`）がアーカイブ済みアクティビティへの新規付与を拒否する。UI経路はTS側でも同じ検証を先に行う
- **アクティビティが変わる時だけ検証する。** 同じアクティビティを保持したままの編集（タイトル・メモの訂正など）、同じ`activityId`を明示的に渡し直す編集は許可する
- MCP経路は事前検証を持たず、DB command境界だけに委ねる（再送の解決をアクティビティ検証より先に行うため）

### アクティビティの完全削除

- 通常のcontext menuから完全削除できる。関連するPlan / Recordの件数を示す確認ダイアログを挟む（destructive）。件数が0件の未使用アクティビティは確認なしで即削除する
- 削除はアクティビティ行のDELETEのみ。関連するPlan / Recordは`activity_id`のFK（`ON DELETE SET NULL`）により「アクティビティなし」になる。時間データそのものは消えない

## カテゴリー

- 色は10色固定パレット（DB CHECK制約・入力バリデーション・UI定数の3箇所で同期）。NULLは未設定（既定色へのフォールバック）
- アイコンはcurated 48種のLucideアイコンから選ぶ
- 所有者整合は複合外部キー（`category_id, user_id`）で担保し、トリガーは使わない

### カテゴリーのアーカイブ

- **カテゴリーをアーカイブしても、所属アクティビティへは道連れしない**（旧タグの親子1階層アーカイブとの明示的な差分）。アーカイブ済みカテゴリーに残る現役アクティビティは、サイドバー・分析ともに未分類バケットへ寄せる
- 既にアーカイブ済みへの操作は冪等no-op。復元時の同名衝突拒否はアクティビティと同様

### カテゴリーの完全削除

- context menuの「アクティビティを追加」を除く操作から実行できる。所属アクティビティ数を示す確認ダイアログを挟む
- 削除はカテゴリー行のDELETEのみ。所属アクティビティは`category_id`のFK（`ON DELETE SET NULL`）により未分類になる

## セグメント（撤去済み）

2026-09-15 に UI / tRPC / MCP（`segments.list`）から撤去した。`/report` のサイドバーがアクティビティ単位のフィルタを持ったことで、「この数個のアクティビティだけで見る」を保存クエリとして別に持つ理由が無くなったため。`segments` / `segment_activities` テーブルと RLS は残っており、drop は不可逆な migration として別変更で扱う。

## 「アクティビティなし」と「未分類」の語彙分離

同じ「分類が無い」状態でも、対象によって語彙を分ける。

| 語彙                   | 対象                      | 判定条件              |
| ---------------------- | ------------------------- | --------------------- |
| **アクティビティなし** | ブロック（Plan / Record） | `activity_id IS NULL` |
| **未分類**             | アクティビティ            | `category_id IS NULL` |

- 「アクティビティなし」のブロックはカレンダーに常に表示され、フィルタ行を持たない。すべての集計に必ず含める（例外なし）。分類を削除するたびに過去の時間が振り返りから目減りしないため
- 「未分類」のアクティビティはサイドバーの未分類見出し配下にテキストのみ（色・アイコンなし）で並ぶ

## サイドバーIA

- 最上部にカテゴリー群。各カテゴリー見出し（色+アイコン+折りたたみ、既定展開）の中に所属アクティビティがネストする
- その下に「未分類」見出しがあり、カテゴリー未所属のアクティビティがフラットに並ぶ
- 末尾に「アーカイブ済み」の折りたたみセクション（復元・完全削除の入口）
- **DnDは廃止**。カテゴリー見出しへのチェックボックス表示もなし
- context menu: アクティビティ行は「このアクティビティだけ表示 / 名前を変更 / カテゴリーを変更（カテゴリーなし含む）/ アーカイブ / 削除」。カテゴリー見出しは「このカテゴリーだけ表示 / アクティビティを追加 / 名前を変更 / 色 / アイコン / アーカイブ」
- 表示フィルタの状態は永続化する。データモデル移行時（タグ→アクティビティのID空間変更）は旧IDを引き継がず全破棄し、次回同期を初回扱いにして全アクティビティを表示状態に戻す

## 検索

削除されていない全期間のPlan / Recordを、メモの部分一致 + 現役アクティビティ名の部分一致で検索する。アーカイブ済みアクティビティの名前では過去ブロックを引けない（旧タグ名での検索は廃止済み。メモ本文に含まれない旧分類名での検索がヒットしなくなった点が、タグからの移行に伴う唯一のユーザー可視の挙動変化）。

## Free / Pro境界

現状、アクティビティ数・カテゴリー数に上限は無い。Free/Pro境界の読み替え（旧タグ数上限の扱い）は epic #2162 の未決事項として保留中。

## MCP

- スコープ `read:activities` 1本が `activities.list` / `categories.list` を束ねる（`segments.list` は 2026-09-15 に撤去）
- `activities.list`: `includeArchived` を受け、`{ id, name, categoryId, isArchived, archivedAt }` を返す。アクティビティ自身は色・アイコンを持たないため、表示には `categories.list` の突き合わせが要る
- `categories.list`: `{ id, name, color, icon, isArchived, archivedAt }`。カテゴリーはブロックへ直接付与されない
- `review.get` はアクティビティ軸で集計し、`isNoActivity` / `isArchived` を各行に含める

## 旧タグモデルの撤去

旧`tags`テーブル、`plans.tag_id` / `records.tag_id`列、tags専有の10関数は`20260903120000_drop_legacy_tags_model.sql`で物理削除した（epic #2162 Step 9、issue #2175）。分類の正本はカテゴリー / アクティビティだけで、tag系のオブジェクトはDBにもコードにも残っていない。

## 関連する意思決定

- タグ→アクティビティ/カテゴリー/セグメントへの3構造全置換を決めた（epic #2162、2026-08-18 User裁可）
- タグアーカイブと削除時の未分類化の設計方針を決めた（削除済み、git履歴参照）（archived_at新設・is_active転用しない理由・削除時の連鎖削除廃止。カテゴリー/アクティビティへも踏襲）
- 機能スコープ: やらないことを決める（削除済み、git履歴参照）（ToDo管理・Kanban等を採用しない理由）

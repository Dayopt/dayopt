# AI開発標準ループ

Dayopt の AI 協働では、agent に変更を書かせることを完了条件にしない。目的・現状・検証方法を先に固定し、変更が必要かを確認してから、必要な範囲だけ実装する。この文書は標準ループの正本で、個別の技術規約は [`AGENTS.md`](../../AGENTS.md) と各 skill を参照する。

## 標準ループ

1. **目的と成功条件を固定する** — Issue / PR がある場合はそこに、ない場合は作業報告に goal、対象範囲、非目標、受け入れ条件、検証方法、外部変更の有無を書く。
2. **現状を確認する** — 実装、設定、既存テスト、git history、必要な実動作を調べる。Issue の想定を現状の事実として扱わない。
3. **作業の種類を選ぶ** — 調査、既知の狭い修正、通常の新機能、高影響変更のどれかを分ける。
4. **必要な場合だけ実装する** — 調査で要件が既に満たされていれば、変更なしで完了できる。差分が必要なら最小の変更を行う。
5. **対象の検証を行う** — 変更後の挙動を、事前に固定した成功条件と独立した検証結果で確認する。
6. **独立レビューを通す** — 通常 PR は GitHub の `@codex review` を使い、対象 SHA を照合して指摘を裁定する。追加 reviewer は起動しない。
7. **人間の判断を残す** — 作るべきか、製品意図、外部への約束、不可逆操作、production / release は人間が判断する。architecture / security の判断も、顧客挙動・公開契約・権限 / プライバシーなどの authority 境界に触れる場合は人間が判断し、それ以外の可逆な内部実装は `AGENTS.md` の authority level に従う。
8. **採用した知見を昇格する** — 現在の差分だけの問題か、再利用可能な規則か、機械化できる契約か、永続的な意思決定かを分類して保存する。

## 作業の種類

| 種類           | 実行すること                                   | 完了の形                                                   |
| -------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 調査・診断     | 再現または現状確認、反証、必要な計測           | 修正、または根拠付きの変更なし。再現不能は未確認事項を残す |
| 既知の狭い修正 | 既存パターンに沿った最小変更、対象検証         | 差分・検証結果・未確認事項を報告                           |
| 通常の新機能   | 目的・設計を確認した最小実装、対象検証         | 差分・検証結果・未確認事項を報告                           |
| 高影響変更     | 下の spec-first 手順、実装、検証、独立レビュー | 凍結した仕様との照合、レビュー裁定、人間判断の記録         |

調査で変更なしとする時は、少なくとも次を残す。

- 試した再現・確認方法とコマンド
- 観測した実装・設定・テストの location
- 要件を満たしていると判断した根拠、または再現できなかった条件
- 未確認事項と次に必要な調査
- 変更した path が無いこと

「再現できない」は「問題が存在しない」と同じではない。部分的に未対応と分かった場合は、変更なしで打ち切らず、必要な最小修正を続ける。

通常の新機能は、既存パターンから外れる設計判断を記録し、影響範囲に応じた対象検証を行う。高影響条件に当たらなければ、不要な spec の凍結は要求しない。

## 高影響変更の spec-first

次のいずれかに触れる変更は、実装前に spec-first を行う。

- auth / RLS / service role、billing / webhook
- migration、data model、公開 API / MCP / OAuth / 外部 provider 契約
- 複数 feature にまたがる architecture・依存方向・state transition
- production state、削除、release など不可逆性を持つ操作

手順は次のとおり。

1. Issue / PR がある場合はそこに、ない場合は作業報告に draft spec と非目標、制約、受け入れ条件、検証方法を書く。
2. 実装・設定・既存契約・テストと突き合わせ、矛盾・不足・古い前提を解消する。
3. 確定した spec と対象 SHA / path を、Issue / PR があればそこに、なければ作業報告に残して凍結する。Issue / PR を後から作成した場合は転記して以後の正本にする。凍結後の仕様変更は、先に spec を更新して再照合する。
4. 担当 agent が実装し、固定した spec の各条件に対して検証する。
5. GitHub の `@codex review` を依頼し、指摘を修正・根拠付き反論・Issue 化のいずれかで裁定する。

spec-first の draft / 凍結は agent 単独の承認ではない。顧客挙動、公開契約、権限 / プライバシーに触れる場合は `CHECKPOINT` として人間の確認を得てから凍結・実装へ進む。production mutation、release、データ削除、実課金は `EXPLICIT AUTHORITY` として、明示指示・独立レビュー・dry-run / backup が揃うまで実行しない。`AGENTS.md` の authority level と独立レビューの条件は別に満たす。

既知の狭い修正や既存パターンへの追従でも、上記の高影響条件に該当する場合は spec-first を行う。高影響条件に該当しない狭い修正、既存パターンへの追従、外部契約を含まない単純な docs / copy 修正には、spec の凍結を要求しない。

## 人間と agent の担当

| agent が担当する                                                          | 人間が担当する                                                                                                                                  |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 検索、再現、コード変更、対象 test / check、整合性確認、レビュー証跡の収集 | 作るべきか、product intent、外部への約束、不可逆操作、production / release。architecture / security は authority 境界に触れる場合のみ人間が判断 |
| 固定した spec に対する実装と機械的な検証                                  | `CHECKPOINT` / `EXPLICIT AUTHORITY` に該当する spec の最終意図、許容リスク、未確認事項を踏まえた採否                                            |

## レビュー知見の昇格

採用したレビュー finding は、PR の中で次のいずれかに分類する。

| finding の性質                | 保存先・対応                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 現在の差分だけの不具合        | 現 PR で修正、または根拠付きで反論                                                                                                         |
| 再利用可能な agent 規則       | `AGENTS.md` または該当 skill を更新                                                                                                        |
| 決定的に検査できる規則        | test、lint、CI、contract check へ移す                                                                                                      |
| 永続的な設計・運用判断        | PR / Issue に候補と根拠を残す。ユーザーが明示的に記録を依頼した場合のみ decision skill を使い、`docs/decisions.md` と該当する stock を更新 |
| 現在の scope 外だが追跡が必要 | 別 Issue を作成し、PR から参照                                                                                                             |

昇格の判断と未対応範囲は PR / Issue に残す。レビューの指摘が無かったこと、または一度修正したことだけを、一般化できた証拠とは扱わない。

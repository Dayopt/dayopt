# AI開発標準ループ

Dayopt の AI 協働では、agent に変更を書かせることを完了条件にしない。目的・現状・検証方法を先に固定し、変更が必要かを確認してから、必要な範囲だけ実装する。この文書は標準ループの正本で、個別の技術規約は [`AGENTS.md`](../../AGENTS.md) と各 skill を参照する。

## 標準ループ

1. **目的と成功条件を固定する** — Issue / PR がある場合はそこに、ない場合は作業報告に goal、対象範囲、非目標、受け入れ条件、検証方法、外部変更の有無を書く。
2. **現状を確認する** — 実装、設定、既存テスト、git history、必要な実動作を調べる。Issue の想定を現状の事実として扱わない。
3. **作業の種類を選ぶ** — 調査、既知の狭い修正、通常の新機能、高影響変更のどれかを分ける。
4. **必要な場合だけ実装する** — 調査で要件が既に満たされていれば、変更なしで完了できる。差分が必要なら最小の変更を行う。
5. **対象の検証を行う** — 変更後の挙動を、事前に固定した成功条件と独立した検証結果で確認する。
6. **必要な独立レビューを通す** — `protected-path-gate.mjs` が外部契約・不可逆・ガードレール変更と判定した PR だけ、required CI が通り head が安定した merge 候補時に GitHub の `@codex review` を使う。通常 PR は依頼せず、追加 reviewer も起動しない。
7. **人間の判断を残す** — 作るべきか、製品意図、外部への約束、不可逆操作、production / release は人間が判断する。architecture / security の判断も、顧客挙動・公開契約・権限 / プライバシーなどの authority 境界に触れる場合は人間が判断し、それ以外の可逆な内部実装は `AGENTS.md` の authority level に従う。
8. **採用した知見を昇格する** — 現在の差分だけの問題か、再利用可能な規則か、機械化できる契約か、永続的な意思決定かを分類して保存する。

実装を始めた主担当が plan → branch → 実装 → 検証 → 後処理まで持つ。モデルを切り替えても担当は変わらない。関連 Issue は同じ変更レーンへ束ねつつ、受け入れ条件と完了状態をIssueごとに追跡し、独立検証・revert・不可逆 migration の隔離が必要な場合だけ分ける。

通常の test / 型検査失敗や資料・環境不足は L2 / L0 で切り分ける。Issue の前提と実測が矛盾する、または未決の契約・設計・scope 判断がある場合は、依存作業を止めて L3 助言へ切り替える。返答は routing / chat-handoff の契約で対象SHA・依頼ID・状態を照合し、partial や参照不能は未確認として扱う。助言は承認済みIssue仕様・人間の承認・authority境界を置き換えない。環境・接続失敗を挙動の合否に数えない。モデルと実行面は利用時に確認し、#2889で測定していない範囲の性能は未検証として記録する。

## 作業の種類

| 種類           | 実行すること                           | 完了の形                                                   |
| -------------- | -------------------------------------- | ---------------------------------------------------------- |
| 調査・診断     | 再現または現状確認、反証、必要な計測   | 修正、または根拠付きの変更なし。再現不能は未確認事項を残す |
| 既知の狭い修正 | 既存パターンに沿った最小変更、対象検証 | 差分・検証結果・未確認事項を報告                           |
| 通常の新機能   | 目的・設計を確認した最小実装、対象検証 | 差分・検証結果・未確認事項を報告                           |
| 高影響変更     | 下の spec-first 手順、実装、検証       | 凍結した仕様との照合、必要なレビュー裁定、人間判断の記録   |

調査で変更なしとする時は、少なくとも次を残す。

- 試した再現・確認方法とコマンド
- 観測した実装・設定・テストの location
- 要件を満たしていると判断した根拠、または再現できなかった条件
- 未確認事項と次に必要な調査
- 変更した path が無いこと

「再現できない」は「問題が存在しない」と同じではない。部分的に未対応と分かった場合は、変更なしで打ち切らず、必要な最小修正を続ける。

通常の新機能は、既存パターンから外れる設計判断を記録し、影響範囲に応じた対象検証を行う。高影響条件に当たらなければ、不要な spec の凍結は要求しない。

## 高影響変更の spec-first

次のいずれかに触れる変更は、実装前に spec-first を行う。

- auth / RLS / service role、billing / webhook
- migration、data model、公開 API / MCP / OAuth / 外部 provider 契約
- 複数 feature にまたがる architecture・依存方向・state transition
- production state、削除、release など不可逆性を持つ操作

手順は次のとおり。

1. Issue / PR がある場合はそこに、ない場合は作業報告に draft spec と非目標、制約、受け入れ条件、検証方法を書く。
2. 実装・設定・既存契約・テストと突き合わせ、矛盾・不足・古い前提を解消する。
3. 確定した spec と対象 SHA / path を、Issue / PR があればそこに、なければ作業報告に残して凍結する。Issue / PR を後から作成した場合は転記して以後の正本にする。凍結後の仕様変更は、先に spec を更新して再照合する。
4. 担当 agent が実装し、固定した spec の各条件に対して検証する。
5. 保護対象 path に一致する場合だけ GitHub の `@codex review` を依頼し、指摘を修正・根拠付き反論・Issue 化のいずれかで裁定する。通常ロジック・時間不変条件・agent 文書は対象 test / CI とセルフレビューで閉じる。

spec-first の draft / 凍結は agent 単独の承認ではない。顧客挙動、公開契約、権限 / プライバシーに触れる場合は `CHECKPOINT` として人間の確認を得てから凍結・実装へ進む。production mutation、release、データ削除、実課金は `EXPLICIT AUTHORITY` として、明示指示・独立レビュー・dry-run / backup が揃うまで実行しない。`AGENTS.md` の authority level と独立レビューの条件は別に満たす。

既知の狭い修正や既存パターンへの追従でも、上記の高影響条件に該当する場合は spec-first を行う。高影響条件に該当しない狭い修正、既存パターンへの追従、外部契約を含まない単純な docs / copy 修正には、spec の凍結を要求しない。

## 現状確認で踏んだ罠

標準ループの 2（現状を確認する）で agent が実際に誤診した形。2026-09-22 に Claude Code の memory から昇格した。

- **依頼された機能に反対の決定が docs に残っていることがある**。実装前に `docs/product/specs/`、`docs/operations/`、`docs/decisions.md` を機能名で grep する。#2775 では催促メール 2 通が specs と rollout 文書の両方で「送らない」と決まっており、代替のアプリ内バナーが動いていて、宛先も 0 人だった。衝突を見つけたら該当行を引用し、代替の実装状況と追加コストを添えて選んでもらう（黙ってどちらかに倒さない）
- **道具起点の issue は how の前に「入れるべきか」を判定する**。依存基準（Star / 更新）は足切りであって価値の根拠ではない。実害（その問題由来の issue・手戻り）、待つ損、gate コスト（誤検知が CI を止める量）の 3 点を実測してから計画を書く（2026-09-15 #2771 は見送り）
- **行数・commit 数・test 行数は「今も要るか」の指標ではない**。撤去候補 5 件のうち 3 件が読み違いだった（2026-09-20 PR #2868）。候補にする前に、workflow なら `on:` の filter まで、参照 issue の open / closed と後継、ファイル冒頭の設計コメントを読む。便益は実走の痕跡（成果物・生成物が repo か issue にあるか）で測る。撤去しない判断も残す
- **「存在しない」は live 応答の keys 列挙でしか主張しない**。OpenAPI spec / docs の欠落は「文書化されていない」まで。Supabase Management API は live 242 キー / spec 237 で、spec 由来の allowlist 射影で値を見ると spec に無いキーは永久に現れない（2026-08-11）。存在確認と値確認で同じ情報源を再利用しない
- **フィールドが埋まっていることは伝播の証拠にならない**。相関 ID は受け手側がフォールバック生成するのが普通で、Supabase の `edge_logs.trace_id` は変更前から 100% 埋まっていた（#2728）。判別力のある測定は、自分で固定した乱数 ID が下流ログに出るか、または `rows / distinct(id)` の before / after
- **429 / クォータ超過を見た時点で容量を結論づけない**。枯れた瞬間の観測に分母は無い。記録するのは事象と時刻だけにし、回復を 1 回観測してから容量・計画への影響を書く。撤回は前言を消さず訂正として残す（2026-09-18 #2827）
- **ファイル数を数える時の 3 つの罠**: `find` は `.git/info/exclude` の worktree を多重計上する、`rg` に `--hidden --glob '!.git/**'` が無いと dot ディレクトリ配下の tracked file が黙って落ちる、`git ls-files | xargs rg` は無音で空を返す。数字には測定条件（対象 glob / 除外）を添える
- **shallow clone の境界 commit は git 考古学を壊す**。`git log -S` / `--follow` が境界（2026-07-15 の 3 commit）へ誤帰属する。`git log -1 --format=%P <sha>` が空なら境界で、帰属は無効。前後の到達可能な commit で `git show <sha>:<path>` を比べる
- **PR 本文は作業後に書かれる**。過去 PR で AI の判断を評価する時、PR 本文を入力にすると人間の答えを読む測定になる。母集団は linked issue のある PR に限り、入力が空になった case は集計から外す（#2827）

| agent が担当する                                                          | 人間が担当する                                                                                                                                  |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 検索、再現、コード変更、対象 test / check、整合性確認、レビュー証跡の収集 | 作るべきか、product intent、外部への約束、不可逆操作、production / release。architecture / security は authority 境界に触れる場合のみ人間が判断 |
| 固定した spec に対する実装と機械的な検証                                  | `CHECKPOINT` / `EXPLICIT AUTHORITY` に該当する spec の最終意図、許容リスク、未確認事項を踏まえた採否                                            |

## レビュー知見の昇格

採用したレビュー finding は、PR の中で次のいずれかに分類する。

| finding の性質                | 保存先・対応                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 現在の差分だけの不具合        | 現 PR で修正、または根拠付きで反論                                                                                                         |
| 再利用可能な agent 規則       | `AGENTS.md` または該当 skill を更新                                                                                                        |
| 決定的に検査できる規則        | test、lint、CI、contract check へ移す                                                                                                      |
| 永続的な設計・運用判断        | PR / Issue に候補と根拠を残す。ユーザーが明示的に記録を依頼した場合のみ decision skill を使い、`docs/decisions.md` と該当する stock を更新 |
| 現在の scope 外だが追跡が必要 | `dispatch` skill に従って別 Issue を作成し、PR から参照                                                                                    |

昇格の判断と未対応範囲は、PR / Issue があればそこに、なければ作業報告に残す。レビューの指摘が無かったこと、または一度修正したことだけを、一般化できた証拠とは扱わない。

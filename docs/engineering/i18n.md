# i18n ガイド — Copy System + next-intl adapter

Dayopt の i18n アーキテクチャ（Copy System / Messages / next-intl adapter / Checks の4層）、ディレクトリ構造、命名規則、namespace 一覧、AI/Agent ルールをまとめる。

---

## i18n アーキテクチャの全体像

Dayopt では `i18n = next-intl` と同一視しない。以下の4層で構成する。

```
i18n architecture
├── Copy System
│   ├── Glossary (docs/product/glossary.md)     ← 表示用。正本は scripts/lib/glossary/terms.ts
│   └── Forbidden Terms (docs/product/glossary.md#禁止表記一覧)
│
├── Messages
│   ├── apps/product/messages/{locale}/{namespace}.json
│   └── apps/web/messages/{locale}/{namespace}.json
│
├── next-intl adapter
│   ├── packages/i18n/                         ← routing / navigation / locale fallback
│   ├── apps/product/src/lib/i18n/request.ts   ← namespace 自動検出
│   └── apps/web/src/platform/i18n/request.ts  ← 固定 namespace loader
│
└── Checks
    ├── pnpm lint:i18n   — 構造整合性（CI 必須）
    ├── pnpm i18n:check  — en/ja キー差分
    ├── pnpm i18n:unused — 未使用キー検出
    └── pnpm copy:check  — 禁止表記スキャン
```

### i18n と next-intl の責務分離

```
i18n
  = 国際化設計全体
  = 表記ルール、翻訳データ、locale、routing、runtime、検査運用まで含む

next-intl
  = Next.js 上で i18n を動かすための実装ライブラリ
  = useTranslations / getTranslations / Provider / routing / request など
```

next-intl の置き換えが起きても Messages と Copy System はそのまま残る。

## Copy System

**Glossary が source of truth**。messages ファイルは「表示するためのデータ」、Glossary は「言葉の正解」。

- UI で使う用語を追加・変更する前に [`docs/product/glossary.md`](../product/glossary.md) を確認する
- 禁止表記一覧は [`docs/product/glossary.md#禁止表記一覧`](../product/glossary.md#禁止表記一覧)
- 違反チェック: `pnpm copy:check`

## 命名規則

### ファイル名

| ルール                  | 例                                                                            |
| ----------------------- | ----------------------------------------------------------------------------- |
| 1 ファイル = 1 ドメイン | `calendar.json` → calendar ドメインのみ                                       |
| 単数形                  | `timeblock.json` ✅（例外: `settings`, `activities`, `shortcuts` は現状許容） |
| camelCase               | `aiChat.json` ✅ / `ai-chat.json` ❌                                          |

### キー構造

```
domain.section.key
```

| 階層 | 説明                         | 例                            |
| ---- | ---------------------------- | ----------------------------- |
| 1    | ドメイン（ファイル名と一致） | `calendar`                    |
| 2    | 画面名 or UI セクション名    | `toolbar`, `modal`, `form`    |
| 3    | 具体的な意味                 | `title`, `description`        |
| 4    | 特殊ケースのみ               | `calendar.toolbar.view.month` |

## 使用方法

### Server Component

```typescript
import { getTranslations } from 'next-intl/server';

export default async function Page({ params }: { params: Promise<{ locale: string }> }) {
  const { locale } = await params;
  const t = await getTranslations({ locale });

  return <h1>{t('calendar.toolbar.today')}</h1>;
}
```

### Client Component

```typescript
'use client';

import { useTranslations } from 'next-intl';

export function CalendarToolbar() {
  const t = useTranslations();

  return <button>{t('calendar.toolbar.today')}</button>;
}
```

### ネームスペース指定

```typescript
// namespace スコープ付き — キーが短くなる
const t = await getTranslations({ locale, namespace: 'calendar' });
t('toolbar.today'); // → calendar.toolbar.today

// スコープ外のキーにはアクセスできない
// t('common.actions.save'); // ← calendar.common.actions.save を探す → NG
```

## メッセージファイルの構造

### 基本ルール

各 JSON ファイルは**ネームスペース名と一致するトップレベルキー**を持つ。

```json
// messages/en/calendar.json
{
  "calendar": {        // ← ファイル名と一致するトップレベルキー
    "toolbar": { ... },
    "event": { ... }
  }
}
```

> **重要**: トップレベルに複数のキーを置かないこと（`common.json` と `email.json` は歴史的例外）。`check-i18n-integrity.ts` が違反を検出する。

### common.json の構造

`common.json` は全 Feature 横断で使う共通キーを管理する。複数トップレベルキーを持つ例外ファイル。

```
common.actions    # 汎用アクション動詞: save, cancel, close, delete, create, edit
common.confirm    # 確認ダイアログテンプレート
common.aria       # アクセシビリティラベル
common.form       # フォーム: required, optional
common.validation # バリデーション
common.errors     # サービスエラー
common.status     # ステータス: loading, success, error
common.time       # 相対時間: today, yesterday, daysAgo
```

**common.json に入れないもの**: カレンダー、振り返り、タイムブロック等の domain 固有キー。

## packages 境界

`packages/components` は next-intl を import しない。翻訳は apps 側の責務。`packages/i18n` だけが framework-bound な adapter として next-intl を知る。

```tsx
// ❌ NG — packages/components で翻訳する
// packages/components/Button.tsx
import { useTranslations } from 'next-intl';
export function DeleteButton() {
  const t = useTranslations();
  return <button>{t('common.actions.delete')}</button>;
}

// ✅ OK — packages/components は children を受け取るだけ
// packages/components/Button.tsx
export function Button({ children }: { children: React.ReactNode }) {
  return <button>{children}</button>;
}

// apps/product 側で翻訳
const t = useTranslations();
<Button>{t('common.actions.delete')}</Button>;
```

## namespace 自動検出（apps/product）

`apps/product/src/lib/i18n/request.ts` は `messages/{locale}/` ディレクトリを自動スキャンしてすべての `.json` を読み込む。手動の NAMESPACES 配列への登録は不要。

```typescript
// request.ts（自動検出）
async function discoverNamespaces(locale: string) {
  // messages/{locale}/ 内の .json ファイルをすべて自動検出
}
```

**apps/web** は `NAMESPACES = ['common', 'legal', 'marketing', 'search']` のハードコード方式を使う（namespace が少ないため）。

## Storybook の messages

`.storybook/decorators/index.tsx` が `import.meta.glob` で `messages/ja/*.json` を自動収集し `NextIntlClientProvider` に渡す。

```tsx
// apps/storybook/.storybook/decorators/index.tsx
const messageModules = import.meta.glob<Record<string, string>>('../../messages/ja/*.json', {
  eager: true,
});
```

**注意**:

- グロブパスは apps/storybook から apps/product/messages/ja/ を指す（Vite のビルド時解決）
- Storybook 専用の fixture ディレクトリは作成していない。product の実 messages を使う
- 新規 namespace を product に追加した場合、Storybook も自動で取り込む（手動登録不要）

## 新規 namespace 追加手順

1. `apps/product/messages/en/{namespace}.json` を作成
2. `apps/product/messages/ja/{namespace}.json` を作成（キー構造は en と完全一致）
3. コードで `useTranslations('{namespace}')` / `getTranslations('{namespace}')` を使う
4. apps/product は自動検出なので追加登録不要

```bash
pnpm i18n:check    # en/ja のキー差分チェック
pnpm lint:i18n     # 構造整合性チェック（CI）
```

## Checks 一覧

| コマンド           | チェック内容                                         | 実行タイミング   |
| ------------------ | ---------------------------------------------------- | ---------------- |
| `pnpm lint:i18n`   | 1-file-1-key 規約、en/ja パリティ、pickMessages 配信 | **CI 必須**      |
| `pnpm i18n:check`  | ファイル単位の en/ja キー差分詳細                    | 翻訳キー変更後   |
| `pnpm i18n:unused` | 未使用キー検出（警告のみ、exit 0）                   | 定期メンテナンス |
| `pnpm copy:check`  | 禁止表記スキャン（警告のみ、exit 0）                 | 翻訳キー変更後   |

## AI/Agent ルール

AI が UI 文言を追加するときのルール:

1. 直接日本語・英語文字列をコードに書かない
2. `messages/{locale}/{namespace}.json` に追加する
3. namespace は画面/機能単位にする
4. `common` に入れるのは共通操作語だけ（domain 固有キーは feature ファイルへ）
5. 新しい用語は [`docs/product/glossary.md`](../product/glossary.md) を確認する
6. 迷ったら既存キーをまず検索する（`pnpm i18n:unused` で重複検出）
7. 最後に `pnpm i18n:check` と `pnpm copy:check` を実行する

## チェックリスト

新しい UI テキスト追加時:

- [ ] [`docs/product/glossary.md`](../product/glossary.md) で用語を確認したか
- [ ] すべての UI 文字列を翻訳キーに置き換えたか
- [ ] `messages/ja/` と `messages/en/` 両方に追加したか（キー構造が完全一致）
- [ ] domain 固有キーを `common.json` に置いていないか
- [ ] 汎用単語は `common.actions.*` を再利用しているか（重複定義していない）
- [ ] Server Component → `getTranslations()`、Client Component → `useTranslations()` を使っているか
- [ ] `pnpm i18n:check` が通るか
- [ ] `pnpm copy:check` で禁止表記が出ていないか

# バグ診断（diagnosing-bugs）

原因調査のループ。**原因が既知の修正に重い診断を課さない。** 上流（mattpocock/skills `diagnosing-bugs`）の骨格を Dayopt 向けに調整した版で、公式原文そのままではない。段階数・仮説数・反復回数を一律に固定しない。

## When to Use

以下の状況で発動:

- 症状は分かるが原因が分からない不具合を調べる時
- UI / tRPC / service / DB / 外部連携のどの層で壊れているか切り分ける必要がある時
- 修正したはずの不具合が再発した時、または Sentry の同じ issue が繰り返し出る時
- 原因未特定の性能 regression を追う時
- 「直したつもりが直っていない」報告を受けた時（再現の signal が無いのが原因であることが多い）

## When NOT to Use

- 原因が既に特定できている修正（そのまま直す。`test` skill で回帰テストを足す）
- UI 文言・型定義のみの変更
- テストの設計・配置・実行そのもの（`test` skill の領域）
- エラー処理の実装（try/catch、tRPC `onError`、ErrorBoundary、Sentry 連携は `error-handling` skill の領域）

## ループ

### 完了状態

この skill はパッチ作成を成功条件にしない。再現・現状確認・反証の結果、要件が既に満たされているなら、**変更なし**を成功状態として根拠付きで報告する。少なくとも確認したコマンド、実装・設定・test の location、判断理由、未確認事項、変更 path が無いことを残す。

再現不能は問題が無いことの証明ではない。再現を阻む条件や未確認事項を `partial` として残し、部分的な未対応が見つかった場合は変更なしで打ち切らず、必要な最小修正へ進む。標準の報告形式は [`AI開発標準ループ`](../../../docs/operations/ai-development-loop.md) §作業の種類を使う。

### 1. 対象症状を検出する signal を作る

**先に「赤くなるもの」を作る。** 症状を検出できるコマンドが無いまま原因を推測しない。

候補（安い順に選ぶ。全部やらない）:

- 既存の失敗している test、または症状を写した新規 test（実行は `pnpm test -- <path>` / `pnpm test:scripts <path>`。自作の runner を書かない）
- `curl` / `pnpm exec tsx` での 1 コマンド再現
- 既存の Playwright spec の 1 ケース
- ローカル fixture（DB が要るなら `USE_LOCAL_DB=true` の条件を満たす）
- 本番ログ / trace の再生

**再現を作るために必要なコード読取は行ってよい。** 読むこと自体は安く、当て推量より速い。

signal の条件: 症状がある時に赤く、無い時に緑。決定的。速い。自分で実行できる。**これが無いまま次へ進まない。**

### 2. 再現して最小化する

再現できたら、要素を 1 つずつ外す。外して症状が消えたら、その要素は原因に関与している。残ったものが最小再現。

非決定的な症状の時だけ、必要な反復回数をその場で決める（何回で十分かは症状の発生率から決める。固定値を持ち込まない）。

### 3. 反証可能な仮説を潰す

- 仮説は「これが真なら X が観測できる」と書ける形にする。観測できない仮説は仮説ではない
- **必要な数だけ立てる。個数を固定しない。** 1 つで足りるならそれでよい
- 確認が安い順に潰す。1 つ潰すごとに signal で再確認する
- 複数層に跨る時は、層の境界（tRPC の入出力、DB の実データ、外部 API の応答）で値を見て、どちら側が壊れているか確定させる

### 4. 計測する

- debugger / 一時ログの順に選ぶ。一時ログは `[DEBUG-xxxx]` のように検索可能な印を付けて、後で全部消す
- 性能の調査は**先に測ってから**直す。推測で最適化しない
- ログ・HAR・認証状態を追加取得する時は `docs/operations/secrets.md` の境界に従い、秘匿値を会話ログへ出さない
- **本番への計測追加・負荷試験・production mutation は自律実行しない**（AGENTS.md の EXPLICIT AUTHORITY）

### 5. 修正の前に回帰テストを置く

原因が確定したら、**修正前に**その症状を検出する test を書く（`test` skill の red → green の規約に従う）。修正してから書くと、その test が本当に症状を検出できるか分からない。

正しい seam が無い（テストを置ける境界が無い）場合は、無理に作らず理由を報告する。

### 6. 再確認して片付ける

- 元の症状（step 1 の signal）と、新しい回帰テストの両方で確認する
- 一時ログ・`[DEBUG-xxxx]`・デバッグ用の分岐を全部消す
- 対象の検証コマンドと出力の要点を報告に添える（「passした」だけの報告は不可）

## 再現できない時

**仮説を確定原因として書かない。** 次を報告する:

- 試した再現方法と、それぞれで観測された結果
- 再現を阻んでいる条件（本番データ、タイミング、外部 state、権限）
- 次に安全に取れる調査（追加ログの設置場所、必要な権限、User の承認が要る操作）

AGENTS.md §レーン運用の停止条件（同種のエラーに 3 回連続で失敗 / scope 外の変更が必要と判明 / 前提と実測が食い違う）に当たったら、試行を続けず報告する。
